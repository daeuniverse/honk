# DNS 灰階與復原操作手冊

本手冊說明 DNS 子系統的灰階部署與復原步驟。子系統本身見 [DNS 設計](../design/dns.md)。

本清單只涵蓋部署流程，尚未在本機開發環境執行。真實 eBPF 的載入與掛接、網路名稱空間變更、透明 socket 和路由 map 發布，都需要一臺隔離、經明確授權且具備 root 權限的 Linux 主機。

## 前置條件

- 一臺可丟棄或隔離的授權主機、一條帶外復原通道，以及一個維護時段。首次灰階不要用共享的正式環境閘道器。
- 只有特權灰階需要以下條件：root 或免密碼 `sudo`；支援 cgroup v2 和原始 BTF 的 Linux 核心，BTF 可以來自核心內建、OpenWrt 的 `/usr/lib/debug/boot/vmlinux`，或用 `HONK_VMLINUX_BTF` 指定的外部檔案；以及真實冒煙測試所需的目標介面、路由和 DNS 用戶端。
- Rust stable、專案 nightly 工具鏈、`rust-src`、`bpf-linker`、CMake、C/C++ 編譯器、libclang/bindgen 依賴和 `readelf`。
- 目前二進位檔、設定、BPF 目標檔案和持久化狀態的確切路徑。狀態在 `<data_dir>/state/`，使用狀態資料庫之前是 `cache.db`。還要留出足以儲存唯讀復原副本的空間，並記下上一份已知可用二進位檔與設定的校驗和。
- 觀察服務日誌和主機健康的途徑。DNS 計數器和結構化日誌只供內部診斷，沒有新增公開的 DNS 指標 endpoint。

## 部署前與備份

1. 記錄主機、核心、介面、目前二進位檔與設定的校驗和、日誌中的目前路由 generation、服務命令和 UTC 時間。
2. 用候選版本的確切原始碼做一次非特權獨立 DNS 冒煙測試：

   ```bash
   just dns-smoke
   ```

   該命令建置 debug 版 `honk-core`，並用 `--mock-ebpf` 啟動真實行程。它分別透過 UDP 和一條持久 TCP 連線，在設定不變的 SIGHUP 前後各驗證一次設定中的 loopback listener。命令返回前會停止行程並清除全部臨時資源。
3. 用一般服務管理器暫停已安裝的服務，把目前二進位檔和設定複製到帶時間戳的唯讀復原路徑。
4. 服務暫停期間備份持久化狀態（`<data_dir>/state/` 或 `cache.db`），並保留擁有權與權限模式。啟用 `global.store_subscribe` 時，還要備份舊的訂閱存放區，也就是 `<data_dir>/.sub`、`/var/share/honk/.sub` 與 `./.sub` 裡第一個找到的私有 `.sub` 目錄。帶狀態資料庫的候選版本首次啟動時會匯入並刪除其中的 `*.sub` 內容。記錄二進位檔、設定、狀態和 `.sub` 備份的校驗和。不要刪除、改寫、壓縮整理或遷移資料庫。
5. 重新啟動舊版本，做完 UDP 和 TCP 的 DNS 冒煙測試，確認復原檔案可用後再繼續。

## 特權灰階

> 狀態：本機開發環境為 **NOT EXECUTED**。下面的步驟只能在滿足全部前置條件、隔離且經明確授權的主機上執行。

1. 在授權主機上建置並檢查候選版本：

   ```bash
   just build-ebpf
   cargo build --release -p honk-core --features ebpf
   ```

   確認 eBPF 目標檔案含 `.BTF`，並保留建置日誌。
2. 正常停止舊服務。安裝候選二進位檔，不要覆蓋復原副本，然後用主機的服務管理器，以保留的正式環境設定和明確指定的 BPF 目標檔案啟動。
3. 確認載入和掛接成功、介面和策略路由正常，新的路由 generation 已發布。不要執行 `just clean-all`，也不要刪除已固定的 map、名稱空間、路由或快取列。
4. 從授權用戶端各發一個 UDP 和一個 TCP DNS 查詢，都走攔截路徑。如果原本就啟用了 Clash，再執行 `/dns/query` 和 `/cache/dns/flush`；不要只為灰階臨時啟用 Clash。
5. 用一般的 SIGHUP 或服務管理器 reload 未修改的設定並重複查詢，再做一次預先批准且可逆的策略變更，reload 後驗證新的完整路由 generation。
6. 觀察內部的低基數診斷：快取命中、未命中、過期；flight 飽和、取消、重試；持久化 drop/flush 失敗；執行時退役；傳輸初始化與重設；投影的舊 generation、寫入失敗、重試；DNS 結果分類。任何持續增長的失敗或重試計數、退役逾時、map 已滿、DNS 應答退化或路由不一致，都判定灰階失敗。

## 復原

1. 正常停止候選版本並保留日誌。不要清理 BPF 狀態，也不要修改持久化狀態。
2. 從已驗證的復原副本還原舊二進位檔和設定。只有灰階損壞或替換了資料庫時才還原資料庫備份，通常保留目前資料庫。帶狀態資料庫的候選版本首次啟動時會匯入並刪除 `cache.db`，啟用 `global.store_subscribe` 時還會刪除舊的 `.sub` 訂閱內容；所以復原到沒有狀態資料庫的版本時，要還原 `cache.db` 和 `.sub` 備份。
3. 用舊設定和 BPF 目標檔案啟動舊二進位檔，再觸發一次一般的設定 reload，讓它重新推送舊路由 generation。重新開放流量前，先從日誌確認 generation 已提交。
4. 重複 UDP 和 TCP 的 DNS 冒煙測試、路由檢查，以及原本已設定時的 Clash 冒煙測試。確認主機健康，並把計數器和日誌與部署前的記錄比較。
5. 為事件檢討儲存候選日誌、校驗和、建置輸出和查詢結果。絕不能把破壞性清理當作復原方式。

## 證據記錄

在部署工單中記錄每條命令、結束狀態、時間戳、校驗和、路由 generation、查詢結果，以及相關計數器和日誌快照。除非已在隔離的授權主機上滿足全部前置條件，否則必須把特權清單標記為 `NOT EXECUTED`。
